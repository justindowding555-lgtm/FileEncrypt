# File deletion audit implementation

Implemented October 7, 2026. This follows the read-only deletion audit and supersedes deletion/publication details in the earlier project audit.

| Finding | Implemented behavior |
| --- | --- |
| P1: Earlier restored ZIP outputs could disappear before source deletion | `PublishedFile` owns the protected output handle across writing, atomic publication, and source cleanup. ZIP restoration retains every successful output guard until the source ZIP removal completes. The same protection applies to ordinary files, bundle creation, and rotation. |
| P1: Directly selected symbolic links could lead to target deletion | Direct selection and planning reject symbolic links and non-regular files. Windows source opens use `FILE_FLAG_OPEN_REPARSE_POINT`, then validate the opened file type and identity, so a final-component link introduced after preflight is rejected. |
| P2: Cancellation did not cover cleanup | Publication checks cancellation after flushing and before rename. Original cleanup checks again after publication, throughout receipt hashing and retries, and immediately before each removal. Cancelling ZIP cleanup stops subsequent removals while preserving completed copies. |
| P2: Temporary and overwrite-backup cleanup failures were silent | Normal failure paths attempt handle-based partial cleanup, briefly retry sharing conflicts, and report the exact retained path if cleanup fails. Atomic overwrite replaces the destination directly, eliminating newly created overwrite backup files. Unwinding has a best-effort cleanup with an error log. |
| P2: A transient initial reader prevented deletion permanently | Sharing conflicts get two bounded retries, reacquiring deletion access and validating identity and bytes. Results distinguish copy success from removed, pending, and retained originals. Session-only retry receipts check identity, size, and SHA256 of both source and saved outputs; retries require no encryption or loaded key. Changed or replaced files block removal. |
| P2: Publication durability before removing sources | Final outputs are flushed before rename and again after rename. Windows creation requests write-through. Unix also synchronizes the destination directory. A final synchronization failure retains the original and reports the published output as durability-uncertain. |
| Unix check-then-unlink race | Automatic original removal is disabled outside Windows. Originals are retained with an explanation because metadata checks cannot supply mandatory sharing protection. |
| Secure-erasure wording | The UI and README continue to describe ordinary filesystem deletion. No overwrite passes or secure-erasure claim were added. |

Windows removal uses the opened source handle. Where supported, POSIX disposition removes its namespace entry when the deleting handle closes. Older filesystems can use legacy deferred disposition; an exact-name directory query detects pending entries without rescanning the entire directory for every source. A failed confirmation query also leaves the status pending. “Check deletion” confirms completion after readers close.

Retry receipts are bounded to 10,000 outstanding originals and are discarded when the app closes. They store paths, identities, sizes, and hashes, with no encryption keys or plaintext file contents. Deletion-enabled operations incur a source/output readback to create receipts; the saved ZIP receipt is cached and shared across its originals. Normal operations without original deletion do not create these receipts. Explicit retries retire changed-file receipts; permissions and missing-drive failures can be retried after the condition is resolved.

The durability changes strengthen the ordering of publication and deletion. They do not establish a guarantee against every hardware, firmware, network-filesystem, or power-loss failure. Power-loss fault injection and non-Windows execution were not performed on this Windows host.

Validation: all **65 Rust unit tests** and **5 frontend unit tests** pass on Windows. Strict library Clippy (`-D warnings`), frontend syntax checking, formatting, and diff whitespace checks pass. Focused regressions cover locked and read-only originals, lock release before deletion, pending removal, changed/replaced originals, changed/missing saved outputs, output protection during retries, late file/ZIP rotation cancellation, ZIP cleanup cancellation, output protection across ZIP restoration, atomic overwrite failure, and explicit retained-plaintext cleanup errors. No application smoke test, dev server, production build, installer, or release package was run.

API references: [handle-based rename](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [extended disposition flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex), [exact-name directory queries](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfilew).
