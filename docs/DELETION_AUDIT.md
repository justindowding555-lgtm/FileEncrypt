# File deletion audit implementation

Implemented October 7, 2026. This follows the read-only deletion audit and supersedes deletion/publication details in the earlier project audit.

| Finding | Implemented behavior |
| --- | --- |
| P1: Earlier restored ZIP outputs could disappear before source deletion | `PublishedFile` owns the protected output handle across writing, atomic publication, and source cleanup. ZIP restoration retains every successful output guard until the source ZIP removal completes. The same protection applies to ordinary files, bundle creation, and rotation. |
| P1: Directly selected symbolic links could lead to target deletion | Direct selection and planning reject symbolic links and non-regular files. Windows source opens use `FILE_FLAG_OPEN_REPARSE_POINT`, then validate the opened file type and identity, so a final-component link introduced after preflight is rejected. |
| P2: Cancellation did not cover cleanup | Publication checks cancellation after flushing and before rename. Original cleanup checks again after publication, throughout receipt hashing and retries, and immediately before each removal. Cancelling ZIP cleanup stops subsequent removals while preserving completed copies. |
| P2: Temporary and overwrite-backup cleanup failures were silent | Normal failure paths attempt handle-based partial cleanup, briefly retry sharing conflicts, and report the exact retained path if cleanup fails. Atomic overwrite replaces the destination directly, eliminating newly created overwrite backup files. Unwinding has a best-effort cleanup with an error log. |
| P2: A transient initial reader prevented deletion permanently | Sharing conflicts get two bounded retries, reacquiring deletion access and validating identity and bytes. Results distinguish copy success from removed, pending, and retained originals. Session-only retry receipts check identity, size, and SHA256 of both source and saved outputs; retries require no encryption or loaded key. Changed or replaced files block removal. |
| P2: Publication durability before removing sources | Final outputs are flushed before rename and again after rename. Windows creation requests write-through. Unix also synchronizes the destination directory. A final synchronization failure retains the original and reports the published output as durability-uncertain. |
| Unix check-then-unlink race | Automatic original removal is disabled outside Windows. Originals are retained with an explanation because metadata checks cannot supply mandatory sharing protection. |
| Secure-erasure wording | The UI and README continue to describe ordinary filesystem deletion. No overwrite passes or secure-erasure claim were added. |

Windows removal uses the opened source handle. Where supported, POSIX disposition removes its namespace entry when the deleting handle closes. Older filesystems can use legacy deferred disposition; an exact-name directory query detects pending entries without rescanning the entire directory for every source. A failed confirmation query also leaves the status pending. The original manual confirmation button was replaced with automatic checks in the October 8 follow-up below.

Retry receipts store paths, identities, sizes, and hashes, with no encryption keys or plaintext file contents. Deletion-enabled operations incur a source/output readback to create receipts; the saved ZIP receipt is cached and shared across its originals. Normal operations without original deletion do not create these receipts. Explicit retries retire changed-file receipts; permissions and missing-drive failures can be retried after the condition is resolved. Receipt lifetime and pending-status checks were refined in the October 8 follow-up below.

The durability changes strengthen the ordering of publication and deletion. They do not establish a guarantee against every hardware, firmware, network-filesystem, or power-loss failure. Power-loss fault injection and non-Windows execution were not performed on this Windows host.

Validation: all **65 Rust unit tests** and **5 frontend unit tests** pass on Windows. Strict library Clippy (`-D warnings`), frontend syntax checking, formatting, and diff whitespace checks pass. Focused regressions cover locked and read-only originals, lock release before deletion, pending removal, changed/replaced originals, changed/missing saved outputs, output protection during retries, late file/ZIP rotation cancellation, ZIP cleanup cancellation, output protection across ZIP restoration, atomic overwrite failure, and explicit retained-plaintext cleanup errors. No application smoke test, dev server, production build, installer, or release package was run.

API references: [handle-based rename](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [extended disposition flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex), [exact-name directory queries](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfilew).

## October 8 follow-up

The subsequent deletion audit found three remaining issues. All three are addressed:

| Finding | Implemented behavior |
| --- | --- |
| P1: Deleting a file discarded NTFS alternate data streams absent from the encrypted copy | Query `FileStreamInfo` through the pinned source handle before receipt creation and immediately before removal. Any named stream retains the original with an explicit explanation and no unsafe retry. Unsupported enumeration only permits deletion if the same handle's volume confirms it has no named-stream support. Unknown providers retain the original. The encrypted format continues to preserve main file contents only. |
| P2: A pending deletion could be misreported as retained after an output changed or disappeared | An accepted deletion has a dedicated status-only poll. Output changes and cancellation cannot relabel it retained or retire its receipt. Once the original name disappears, report removed. If a different file now occupies that name, confirm the original's removal without deleting the replacement. |
| P2: Stale receipts from replaced reports exhausted the 10,000-entry registry | Stage each new report's receipts separately. Commit them when a completed report replaces the displayed results, retiring the previous report's receipts. On failure, discard the staged receipts and preserve the still-displayed report's retries. Both maps are bounded to 10,000 entries each, so a full previous report cannot prevent new retry IDs. A report exceeding its own limit gets an explicit explanation. Closing the app clears all receipts. |

On Windows, the checkbox requests ordinary deletion after successful publication, bypassing the Recycle Bin. Removed, retained, and pending are distinct outcomes. A pending deletion can finish after another reader closes even if a subsequent status check is cancelled. Checking the box does not override safety checks, sharing locks, read-only attributes, permissions, or the policy to preserve extra data streams. Key rotation only cleans up selected encrypted inputs; it keeps the old key file.

Regression coverage includes empty and nonempty files with alternate streams, streams added before an explicit retry, decryption and file rotation, mixed ordinary/alternate-stream bundle inputs, ZIP restoration and rotation, pending checks with changed/missing outputs and cancellation, replacement files at a previously deleted path, receipt capacity across reports, and rollback after a failed report. All filesystem fixtures are disposable.

Pending deletions now update automatically. A single frontend timer checks up to 100 receipts per second, rotating across all result pages. It pauses new checks while another action is busy, leaves controls available during an in-flight check, avoids redrawing unchanged rows, and backs off to at most ten seconds after transient command errors. Checks stop when no pending receipts remain or results are replaced. There is no pending confirmation button; retained originals keep a separate explicit retry.

The `check_pending_deletions` command is read-only with respect to files: it checks accepted deletions only, never retries a retained original, and never hashes saved outputs. Shared receipt snapshots keep filesystem queries outside the registry mutex and the file-job slot. IDs remain stable across polls. Confirmed outcomes are cached for the current report so lost responses cannot lose confirmation; the cache is bounded by that report's existing receipt IDs and cleared with the report. Results from an obsolete report cannot overwrite newer UI results or resurrect old backend receipts.

Additional regressions cover automatic confirmation after a real Windows reader closes, removed saved outputs, unchanged job/cancellation flags during checks, recoverable confirmation after a lost response and replacement file, retained receipts remaining untouched, frontend batching across pages, job pauses, concurrent job completion, stale responses, expired receipts, and error backoff.

Validation: **75 Rust unit tests** and **10 frontend unit tests** pass on Windows. Strict library Clippy (`-D warnings`), frontend syntax checking, formatting, and diff whitespace checks pass. No application smoke test, dev server, production build, installer, or release package was run. Non-Windows execution and network-filesystem fault injection were not performed on this host.

API references: [stream-list layout](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_stream_info), [stream enumeration and the empty-list result](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [volume stream capability](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew).
